# Handoff — Sessão 2026-08-31

## Objetivo geral

O projeto é o **population-pyramid**, uma ferramenta que gera pirâmides demográficas de população de software. O diretório `coleta-dados/` é um pipeline de mineração independente que coleta eventos de repositórios Clojure via GitHub REST API e git clone, produzindo CSVs intermediários.

Esta sessão focou em duas áreas:

### Sessão anterior (2026-08-30)

1. Adicionar 4 novos tipos de evento (comentários e eventos de issues)
2. Trocar `repo_id` texto por `repo_id` numérico (id imutável do GitHub)
3. Trazer o percentual de cada linguagem do repositório (JSON bruto do GitHub)
4. Data de coleta em formato único (timestamp de corte em UTC)

### Sessão atual (2026-08-31)

1. **Refatorar `main()`** da etapa_2 para legibilidade (extração de funções auxiliares, `collections.Counter`)
2. **Separar coleta em dois scripts paralelos**: etapa_2A (GitHub REST API) e etapa_2B (git clone)
3. **Criar módulo compartilhado** `common.py` com infraestrutura (sessão API, paginação, progresso, CSV)
4. **Criar orchestrator** que roda os dois scripts em paralelo e faz merge dos CSVs

## Decisões tomadas

| Decisão | Escolha | Motivo |
|---|---|---|
| Delimitador do CSV | `\|` (pipe) | Código já usava; CSVs existentes serão regenerados |
| Coluna `language` | Adicionar ao CSV | commit_comments e pr_comments: extensão do path; issue_comments e issue_events: linguagem do repo |
| Retomabilidade | Tudo do zero (etapa_1 + etapa_2) | Usuário quer regenerar todos os dados |
| Grafia `event_type` | Singular: `commit_comment`, `pr_comment`, `issue_comment`, `issue_event` | Compatibilidade com CSV atual (`issue`, `pr`, `commit`) |
| `path` None em comentários | Language fica vazio | Mais honesto que adivinhar |
| `repo_id` | Numérico (`item['id']`), texto vira `repo_name` | `id` do GitHub é imutável; `full_name` muda com rename/transfer |
| Progress JSON | Chave é `repo_id` numérico, valor inclui `repo_name` | Estabilidade + legibilidade |
| Afetar scripts auxiliares | Sim (contar_repos.py etc.) | Consistência |
| Formato de `languages` | JSON bruto do GitHub (`{"Clojure":12345,"Java":67890}`) | Preserva bytes originais; percentual pode ser calculado no leitor |
| Data de coleta | Coluna `collection_started_at` no CSV + timestamps no progress JSON | Permite comparar duas coletas e saber se períodos são disjuntos |
| Separar API e git | Dois scripts paralelos com CSVs separados + merge | Perfis de recurso diferentes; paralelismo evita competir por rate limit |
| Progresso separado | `etapa_2A_progresso.json` e `etapa_2B_progresso.json` | Evita race condition; cada script tem status independente |
| Commits ficam no script git | `author_email` extraído do clone local (`%ae`) | Dados 100% locais; zero requisições HTTP na etapa_2B |
| Infraestrutura em módulo | `common.py` com toda a base compartilhada | Evita duplicação entre os dois scripts |

```
  eventos_repositorios.csv     # merge dos dois
  reports/
    etapa_2A_progresso.json    # progresso do script API
    etapa_2B_progresso.json    # progresso do script git
```

## Schema dos CSVs

### `repositorios_clojure_alvo.csv` (saída da etapa_1)

```
repo_id|repo_name|repo_url|clone_url|default_branch|size_kb|stars|watchers|clojure_ratio|languages|total_commits|lifespan_days|num_contributors|top_contributor_ratio|collected_at|about|tree_scan_status|...
```

A coluna `languages` contém JSON bruto do GitHub: `{"Clojure":12345,"Java":67890,...}`.

### `eventos_api.csv` e `eventos_git.csv` (saídas da etapa_2)

```
repo_id|repo_name|event_type|number|title|author|author_login|author_email|created_at|state|sha|message|url|labels|files|language|collection_status|collection_started_at
```

Ambos os CSVs têm o mesmo schema. O `eventos_repositorios.csv` é a concatenação dos dois.

Na etapa_2A, `author_login` é preenchido com o login do GitHub e `author_email` fica vazio. Na etapa_2B, `author_login` fica vazio e `author_email` é extraído do clone local.

A coluna `collection_started_at` registra o momento (UTC) em que a execução da etapa 2 iniciou. Permite comparar duas coletas.

## Schema do progress JSON

```json
{
  "collection_started_at": "2026-08-30T14:00:00+00:00",
  "collection_ended_at": "2026-08-30T16:30:00+00:00",
  "updated_at": "...",
  "repositories": {
    "12345678": {
      "repo_name": "tonsky/FiraCode",
      "status": "complete",
      "branch": "master",
      "error": "",
      "updated_at": "..."
    }
  }
}
```

Cada script tem seu próprio arquivo de progresso (`etapa_2A_progresso.json` e `etapa_2B_progresso.json`). Um repositório pode ser `complete` no API mas pendente no git, e vice-versa.

## Estrutura de runs

`run.sh` recebe nome como argumento: `./run.sh 2026-08-30-clojure`. Cada run cria uma pasta independente em `runs/`. Runs anteriores não são afetadas.

O orchestrator pode ser chamado isoladamente:
```bash
python scripts/etapa_2_orchestrator.py runs/2026-08-30-clojure
```

Os scripts individuais também funcionam sozinhos:
```bash
python scripts/etapa_2A_eventos.py runs/2026-08-30-clojure
python scripts/etapa_2B_eventos.py runs/2026-08-30-clojure
```
